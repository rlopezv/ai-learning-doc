## Context

Artificial intelligence is increasingly becoming a core component of modern software systems. Applications such as intelligent assistants, document analysis tools, coding copilots, and enterprise knowledge systems rely on AI models to interpret language, reason over information, and generate responses.

However, building production AI applications involves far more than simply calling a model API. Modern AI systems integrate multiple components including prompts, retrieval pipelines, orchestration workflows, external tools, evaluation datasets, and monitoring infrastructure. The behavior of these systems emerges from the interaction of these components rather than from deterministic program logic.

This chapter introduces the discipline of **AI Systems Engineering**, which focuses on designing, building, and operating reliable AI-powered applications. It explains how modern AI systems differ from traditional software systems and provides the architectural foundations needed to understand the rest of the book.

---

Modern AI applications are built from multiple interacting components that collectively produce intelligent behavior. Models, prompts, data pipelines, and orchestration logic interact to generate responses and perform tasks for users.

In contrast to traditional applications, the behavior of AI systems is shaped not only by code, but also by **data, prompts, models, and evaluation artifacts**. Managing these artifacts and their interactions is the core responsibility of AI Systems Engineering.

---

## Concept Overview

Traditional software systems are **deterministic**: program logic fully determines system behavior. If the same input is provided twice, the program produces the same output.

AI systems behave differently. Their outputs are generated by **probabilistic models trained on large datasets**, meaning behavior emerges from statistical patterns learned during training rather than from explicit rule-based algorithms.

Large Language Models (LLMs) are typically **autoregressive transformer models trained to predict the next token in a sequence**. Despite this relatively simple training objective, large-scale training leads to emergent capabilities such as language understanding, reasoning, summarization, and code generation.

Because of these capabilities, modern AI systems are rarely composed of a single model invocation. Instead, they combine multiple interacting components that collectively determine system behavior.

These components commonly include:

- application logic
- prompts
- machine learning models
- retrieval systems
- orchestration workflows
- external tools and APIs
- evaluation pipelines
- monitoring and observability systems

Together these components form a **composite system**, where behavior emerges from interactions between system artifacts rather than from a single algorithm.

### Mental Model

A useful way to understand AI systems is to think of them as pipelines that transform **user intent into responses**.

```id="5hez2a"
User Intent
↓
Context Construction
↓
Model Reasoning
↓
Response Generation
```

Each stage of the pipeline contributes information that shapes the final output. In practice, this pipeline is implemented through multiple services and artifacts working together.

A simplified conceptual flow illustrates how these components interact:

```id="0fsowh"
User Input
    ↓
Application Logic
    ↓
Prompt Construction
    ↓
Context Retrieval
    ↓
LLM Inference
    ↓
Response Generation
```

The central engineering challenge is therefore not only implementing these components, but ensuring they **interact reliably, predictably, and efficiently** under real-world workloads.

### Example AI System

A typical AI application illustrates how these components interact in practice:

```id="0e5lyy"
User Query
    ↓
Application Service
    ↓
Orchestrator
    ↓
Retriever
    ↓
Vector Database
    ↓
Context Builder
    ↓
LLM
    ↓
Response
```

In a real production environment, additional subsystems are often present, including:

- API gateways and request routing
- caching layers to reduce model calls
- safety filters and moderation systems
- response post-processing
- tool execution systems (APIs, calculators, databases)
- monitoring and logging infrastructure

These components ensure that AI systems remain **secure, observable, and cost-efficient** in production.

In this simplified architecture:

- the **application service** manages user interaction and request handling
- the **orchestrator** coordinates system workflows
- the **retriever** searches for relevant knowledge
- the **vector database** stores semantic embeddings
- the **context builder** assembles retrieved information into model input
- the **LLM** performs reasoning and response generation

Modern AI systems frequently extend language models with **external tools**, allowing them to interact with APIs, databases, and computation systems. These tools enable AI systems to perform actions that go beyond text generation.

Later chapters examine these components in detail, including **Prompt Engineering**, **Retrieval-Augmented Generation (RAG)**, **Workflow Systems**, and **Agent Architectures**.

**Key Concept — AI Systems Are Composed Systems**

A production AI application is rarely just a model invocation. Instead, it is a network of artifacts and services: prompts, embeddings, vector databases, orchestration logic, evaluation datasets, monitoring pipelines, and infrastructure.

Managing and evolving this ecosystem is the core responsibility of **AI Systems Engineering**.

## 1.1 A Paradigm Shift in Software Engineering

Understanding modern AI systems requires recognizing that software engineering itself has undergone a significant paradigm shift.

Traditional software engineering is based on deterministic algorithms:

```id="we0sm8"
Input → Algorithm → Output
```

Developers explicitly define how inputs are transformed into outputs through program logic.

However, many real-world problems are difficult to solve using explicit rules alone, including:

- natural language understanding
- document analysis
- summarization
- conversational interaction
- knowledge extraction

Machine learning introduced a different paradigm: behavior is **learned from data rather than explicitly programmed**.

Large language models extend this paradigm by providing **general-purpose language and reasoning capabilities** that can be adapted to new tasks using prompts and contextual information rather than task-specific model training.

This shift fundamentally changes how software systems are designed and evaluated.

| Traditional Software            | AI Systems                            |
| ------------------------------- | ------------------------------------- |
| Deterministic logic             | Probabilistic models                  |
| Behavior defined by code        | Behavior shaped by data and prompts   |
| Unit tests verify correctness   | Evaluation frameworks measure quality |
| Algorithms implemented manually | Capabilities emerge from training     |

Because of this shift, AI systems must be engineered as **probabilistic systems**, where quality is measured statistically rather than guaranteed deterministically.

As a result, building AI applications requires **new engineering practices, evaluation methods, and architectural patterns**.

---

## 1.2 What is AI Systems Engineering

Given this paradigm shift, a new engineering discipline has emerged: **AI Systems Engineering**.

AI Systems Engineering focuses on building reliable production systems that integrate AI models as core components.

It extends traditional software engineering with responsibilities such as:

- integrating model inference into application services
- designing prompt and context pipelines
- operating retrieval infrastructure
- integrating external tools and APIs
- managing model lifecycle and updates
- evaluating system behavior
- monitoring quality, performance, and cost

The discipline sits at the intersection of several engineering domains:

- software engineering
- machine learning engineering
- distributed systems engineering
- data engineering
- platform engineering
- DevOps and MLOps

In practice, an AI system may include components such as:

- model inference services
- prompt management systems
- context retrieval pipelines
- orchestration workflows
- evaluation datasets
- observability and monitoring platforms
- safety and security guardrails

**Key Concept — Models Are Only One Component**

In most production AI systems, the model itself is **not the primary source of complexity**. The majority of engineering effort lies in the surrounding infrastructure required to control, evaluate, and operate model behavior safely and reliably.

### AI System Reliability

Unlike deterministic systems, AI systems cannot guarantee exact correctness for every input. Instead, engineers reason about **system reliability and performance characteristics**.

Typical reliability dimensions include:

- response accuracy
- hallucination rate
- retrieval relevance
- latency
- token usage
- cost per request

These metrics describe **system behavior under real workloads**, rather than strict correctness of individual outputs.

## 1.3 The Convergence of Engineering Disciplines

Building reliable AI systems requires expertise from several historically separate engineering domains.

```id="cck0s8"
AI Systems Engineering
        │
        ├── Software Engineering
        ├── ML Engineering
        ├── Data Engineering
        └── Infrastructure Engineering
```

Each discipline contributes distinct capabilities:

- **Software Engineering** — application architecture, APIs, and system design
- **Machine Learning Engineering** — model development, training, and evaluation
- **Data Engineering** — data pipelines, storage, and data quality
- **Infrastructure Engineering** — scalable compute, networking, and deployment platforms

AI Systems Engineering integrates these areas to produce **coherent end-to-end systems** capable of operating reliably at scale.

As AI systems grow more complex, additional concerns such as **observability, cost management, and security** become equally important. Engineers must understand how to measure system behavior, detect regressions, and control operational costs.

## 1.4 From Software 1.0 to LLM Systems

To better understand why modern AI systems require new engineering approaches, it is useful to examine the historical evolution of software systems.

The evolution of software systems can be understood through three conceptual stages.

**Software 1.0**

```id="ycd48z"
Code + Input Data → Output
```

**Software 2.0**

```id="okrw37"
Training Data + Learning Algorithm → Model
Model + Input → Output
```

**LLM Systems**

```id="8efhb9"
Model + Prompt + Context → Output
```

In LLM-based systems:

- the **model** provides general reasoning capabilities
- the **prompt** defines instructions and task structure
- the **context** provides task-specific or domain-specific information

System performance therefore depends heavily on **prompt design, context construction, and retrieval quality**, not only on the model itself.

Modern systems often extend this architecture with **tool usage**, where models interact with external systems such as:

- APIs
- databases
- calculators
- code execution environments

These tools allow AI systems to interact with external systems and perform actions beyond text generation.

## 1.5 New Categories of System Artifacts

Traditional software systems primarily manage two artifact types: **source code and data**.

AI systems introduce additional artifacts that directly influence system behavior. Understanding these artifacts is essential for reasoning about how AI systems behave and how they evolve over time.

| Artifact Type       | Purpose                                                   |
| ------------------- | --------------------------------------------------------- |
| Prompts             | Define instructions and behavioral constraints for models |
| Embeddings          | Numerical semantic representations of text or data        |
| Vector indexes      | Enable semantic similarity search                         |
| Evaluation datasets | Measure system quality and performance                    |
| Retrieval pipelines | Provide contextual knowledge to models                    |
| Model checkpoints   | Store trained model states                                |

These artifacts collectively determine system behavior and must be **versioned, tracked, and evaluated** as part of the engineering process.

For example, changing a prompt template or updating a vector index may alter system outputs even if the application code remains unchanged.

### Example

Consider an internal AI assistant that answers questions about company policies.

The system behavior depends on multiple artifacts:

- the **prompt template** used to instruct the model
- the **retrieved documents** from the knowledge base
- the **model version** used for inference
- the **evaluation dataset** used to measure system quality

Changing any of these artifacts can change the response produced by the system.

Effective AI engineering therefore requires managing **artifact dependencies and experiment tracking**.

## 1.6 The Artifact Dependency Graph

Because AI systems depend on many interacting artifacts, it is useful to think of them as **dependency graphs**.

This perspective helps engineers understand how changes in prompts, retrieval pipelines, or models propagate through the system.

```id="tjcphs"
User Query
    ↓
Prompt Template
    ↓
Retrieved Context
    ↓
Model
    ↓
Generated Response
```

Each node in this graph represents a **versioned component**.

Changing any component—such as a prompt template, retrieval strategy, or model version—can alter system outputs.

For example, modifying a prompt template may:

- change how retrieval queries are generated
- alter the reasoning path used by the model
- increase token usage and latency
- modify response quality

### Failure Example

This dependency perspective also helps explain common system failures.

```id="rzljf7"
User Question
↓
Retriever returns irrelevant document
↓
LLM receives incorrect context
↓
Model generates an incorrect answer
```

Even though the model is functioning correctly, the overall system produces the wrong result because the **retrieval component failed**.

This illustrates an important insight: many AI system failures originate from **interactions between components**, rather than from a single faulty model.

In more advanced systems, additional nodes may appear in the dependency graph, such as:

- embedding models
- vector indexes
- tool execution outputs
- safety filters
- response post-processing

**Key Concept — Behavior Emerges from Artifact Interactions**

AI systems do not behave like deterministic programs. Their behavior emerges from **interactions between prompts, context, models, and data pipelines**.

Understanding these dependencies is essential for debugging, evaluating, and improving AI systems.

## 1.7 The Eight-Layer Architectural Model

To reason about complex AI systems, responsibilities can be organized into architectural layers.

```id="irvtwc"
Interaction Layer
Application Layer
Orchestration Layer
Prompt Layer
Retrieval Layer
Model Layer
Data Layer
Infrastructure Layer
```

Separating responsibilities into layers improves **modularity, scalability, and maintainability**.

Each layer addresses a different concern:

- **Interaction Layer** — user interfaces and external integrations
- **Application Layer** — business logic and APIs
- **Orchestration Layer** — workflow coordination and system control
- **Prompt Layer** — structured instructions and prompt templates
- **Retrieval Layer** — external knowledge and contextual information
- **Model Layer** — model inference and reasoning
- **Data Layer** — storage of documents, embeddings, and datasets
- **Infrastructure Layer** — compute, networking, and storage resources

This layered model is inspired by classical system architecture approaches used in distributed systems and cloud platforms.

- **Platform and Infrastructure** — operating AI systems in production

The stack therefore acts as a **reference architecture** for reasoning about AI applications.

## 1.8 The AI System Lifecycle

Designing the architecture of an AI system is only part of the challenge. Engineers must also manage how these systems evolve over time.

AI systems follow a lifecycle that extends beyond traditional software deployment.

Typical phases include:

1. problem definition
2. dataset and knowledge preparation
3. model selection or training
4. prompt design
5. retrieval system design
6. evaluation dataset creation
7. system integration
8. deployment
9. monitoring and evaluation
10. iterative improvement

In practice, AI systems operate in a **continuous improvement loop**.

```id="zrpvmh"
Build System
↓
Evaluate Behavior
↓
Deploy
↓
Observe Production Signals
↓
Improve System
↺
```

Unlike conventional software systems, **evaluation and iteration remain continuous activities**. System performance may change when prompts are updated, retrieval data evolves, or models are replaced.

Effective AI engineering therefore requires **continuous measurement and experimentation**, often supported by automated evaluation pipelines.

## 1.9 New Engineering Challenges

Because AI systems are probabilistic and artifact-driven, they introduce challenges that rarely appear in deterministic software.

| Challenge             | Description                                             |
| --------------------- | ------------------------------------------------------- |
| Non-determinism       | Model outputs may vary between executions               |
| Prompt sensitivity    | Small prompt changes can significantly alter behavior   |
| Hallucination         | Models may generate incorrect or fabricated information |
| Context limitations   | Models process only a limited number of tokens          |
| Cost and latency      | Model inference may be computationally expensive        |
| Evaluation difficulty | Quality may be subjective or domain-dependent           |

### Common Failure Modes

AI systems can fail in ways unfamiliar to traditional software systems:

- hallucinated or fabricated responses
- retrieval returning irrelevant context
- prompt injection attacks
- context window overflow
- incorrect tool or API usage
- data leakage or unsafe responses

These failure modes highlight the importance of **evaluation frameworks, guardrails, observability systems, and security controls** in production AI systems.

## 1.10 Design Principles for AI Systems

Building reliable AI systems requires engineering practices that account for the probabilistic and artifact-driven nature of modern AI architectures. Several design principles consistently appear in successful production systems.

### Artifact Versioning

AI systems depend on multiple artifacts beyond source code, including prompts, datasets, embeddings, and evaluation sets. These artifacts must be versioned and tracked to ensure reproducibility.

Without artifact versioning, it becomes difficult to understand why system behavior changes after updates.

Key artifacts to version include:

- prompt templates
- retrieval datasets
- embedding models
- vector indexes
- evaluation datasets
- model versions

### Evaluation-First Development

Traditional software development emphasizes unit testing. AI systems require **evaluation pipelines** that measure system quality using representative datasets.

Instead of verifying strict correctness, evaluation frameworks measure metrics such as:

- response accuracy
- hallucination rate
- retrieval relevance
- task completion success

Engineering teams should design evaluation datasets early and use them to detect regressions during system iteration.

### Observability by Design

Because AI systems are probabilistic, monitoring runtime behavior is essential.

Observability systems help engineers understand how the system behaves in production by tracking:

- prompts and model inputs
- model outputs
- token usage
- latency
- cost per request
- error rates

These signals allow teams to identify quality regressions, unexpected behaviors, or operational inefficiencies.

### Modular Architectures

AI systems evolve rapidly. Models change, prompts improve, and retrieval strategies evolve.

Designing modular architectures allows individual components to be replaced without rewriting the entire system.

Common modular components include:

- model providers
- retrieval systems
- prompt templates
- evaluation pipelines
- tool integrations

Modularity enables faster experimentation while maintaining system stability.

## Chapter Summary

- **AI Systems Engineering** is the discipline of designing, building, and operating production systems where AI models are core components.
- Modern AI applications are **composed systems** that combine prompts, models, retrieval pipelines, orchestration workflows, tools, and application logic.
- System behavior emerges from interactions between artifacts such as prompts, datasets, retrieval pipelines, and models.
- The **Artifact Dependency Graph** helps explain how changes in one artifact can influence the entire system.
- The **eight-layer architectural model** provides a structured framework for reasoning about AI system components.
- AI systems introduce new engineering challenges including non-determinism, hallucinations, evaluation complexity, operational cost, and system observability.
- Successful AI platforms follow design principles such as artifact versioning, evaluation-first development, observability, and modular system architecture.
